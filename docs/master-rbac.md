# Master tags and feature access

Superadmin → Master creates tags, lists definitions and edits feature permissions. Profiles retains tag assignment and account support, and creates administrator profiles.

Individual and Organisation are chosen during first-time profile setup. Workspace deployments use the existing workspace choice; deployments without workspaces save the account profile type. Users see one choice, and neither type is an assignable tag. University, Hospital, Contributors, Standard, Founders, Special, Hero, God, Fraud, Scammer, Narration Setter, Gov-Departments, Commercial/Enterprises, Community and Manufacturer are independent tags. The existing Private profile tag remains available. Master uses a flat list and opens creation/editing in a popup without parent or built-in labels.

The seven permissions cover profile/public page editing, content/files/activity, AI knowledge/visitor Q&A, Store/orders/payments, enquiries, invites/suggestions and jobs. Each assigned tag must allow a feature. Untagged accounts follow Standard. Defaults retain existing Studio access; Superadmin can restrict any role. Account settings and platform support remain available to profile administrators. Contributors can add their own files and articles, without settings or private profile information. Profile type selection does not grant feature permissions.

Every signed-in request reloads current role permissions from the database. UI navigation refreshes on window focus. Workspace membership roles and tag permissions must both allow an action. Website connections and source access policies require knowledge permission; team tools require community permission. The Studio assistant, combined analytics, webhooks and data exports require all feature permissions because they access multiple areas. Workspace selection remains accessible. Shared page writes separately enforce Store and activity permissions; content-only accounts use a limited activity API. Delivery assets require Store access.

The internal Profile Creator tag grants the separate `profiles.create` platform capability and no Studio permissions. It exposes only Profiles in Superadmin. Full Superadmin can grant this capability through a tag's permission popup or a profile's edit popup. Created accounts remain pending until full Superadmin approves them; creators cannot approve, edit existing accounts or access other platform tools. Internal tag labels and definitions are removed from public responses. See [Jobs and profile creation](jobs-profiles.md) for installation and approval details.

For an existing database, run `supabase/master-rbac.sql` after `admin-experience.sql`, followed by the workspace prerequisites and `supabase/jobs-profiles.sql` before releasing this application. It preserves assignments and privacy, and reruns preserve edited permissions. An existing custom tag with a newly reserved name receives a unique `(custom)` suffix; its key, assigned accounts and access rules remain unchanged. Once the jobs migration is applied, rerun that migration last if applying older migrations again.

Validation: `npm test`, `npm run build`. Browser fixture: `npm run dev:web` then `/tests/browser/governance.html?role=owner&view=/superadmin/master`.

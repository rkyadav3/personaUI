# Platform dashboard setup

Run `supabase/platform-governance.sql` in the Supabase SQL editor after `multitenant.sql`, `registration.sql` and `events-commerce.sql`, before deploying these changes. It adds account tags, suggestion storage, invite identity snapshots, atomic invited registration, main-site settings and a financial ledger. The application uses the service-role server client; these records are unavailable to anonymous database clients.

Then run `supabase/studio-chat.sql` if it is not installed, followed by `supabase/admin-experience.sql` and `supabase/knowledge-visibility.sql`. The first adds registered custom tags, computed profile privacy, activity snapshots and assistant insights. The second checks current source publication during keyword/vector retrieval and removes stale chunks transactionally on unpublish/delete. These migrations have been source-reviewed locally; they have not been applied to a live database.

Run `supabase/security-hardening.sql` after `platform-governance.sql`, `home.sql` and `studio-assistant.sql`, **before deploying the matching server**. It adds service-only atomic login finalization and serializes offering rating aggregation. The new login code fails closed if `finalize_login` is unavailable; apply this migration before deploying or existing users cannot sign in. SQL execution and concurrency have not been verified against a live database.

Set `SUPERADMIN_EMAILS` to the platform owner's login email(s). SuperAdmin and Admin are mutually exclusive: all other registered accounts are profile admins. For existing installations without `SUPERADMIN_EMAILS`, the old `ADMIN_EMAILS` list retains owner access until an explicit owner list is configured. Never put service keys in `VITE_*` variables.

Public registration rejects configured owner email addresses, including the legacy owner fallback. It cannot establish ownership merely by typing a privileged email. Existing owners sign in normally. For first setup, the platform operator must provision the owner in `public.users` through the trusted server/database with a bcrypt password hash (cost 12), a unique slug and the configured owner email. Never store a plaintext password or use a public invitation as owner provisioning. Owner access continues to be derived from the server configuration.

The SuperAdmin dashboard is `/superadmin`, with Customers, Sales & payments, Invite links, Suggestions and Main site settings pages. Owners have no personal Studio, public profile or knowledge persona; existing owner profile data is retained but is unavailable publicly. Owners entering `/admin` are redirected to `/superadmin`, and personal Studio operations reject them. The owner can support customers by editing details, resetting passwords, suspending/restoring access and assigning any combination of Hero, Special and Private profile tags. Hero and Special remain public; Private takes precedence and limits profile and knowledge access to that customer and the SuperAdmin. A suspended account cannot sign in or appear publicly. Publishing and existing field visibility controls still apply.

Customers includes **Add new tag** with a name (up to 40 characters) and Public or Private visibility. Registered tags appear in account filters and assignment controls; public badges use the saved label on directory cards and profiles. Any private tag wins over public tags. The database computes `users.profile_private`; public reads fail closed if a custom-tagged account lacks that value. Updating a registry visibility in the database recomputes affected accounts. Built-in definitions and tag keys cannot be altered; there is no tag deletion/editing UI.

Every profile admin can use `/admin/invites` and `/admin/suggestions`, including before completing a profile. Admins see and revoke their own invite links and view their own invited-member log. The SuperAdmin can create invites and sees all links and joins in `/superadmin/invites`. Creating an invite records the authenticated creator, and registration locks the invite, creates the account, consumes one use and logs the invited member in one transaction. Existing joins are backfilled. Identity snapshots and logs survive account deletion; previously deleted accounts cannot be reconstructed by the migration.

Admin Invite links and Suggestions are grouped under **Community**, outside Settings. **Content & knowledge → Content** combines Articles, Templates and Research topics in one workspace with three named tabs. Templates provide reusable article structure, while topics organize related articles and files. Newly created topics are available in article selectors when switching back. Existing article/template/topic URLs remain supported.

Suggestions support Add, Remove and Update. Only admins can submit them. Senders see their own suggestions and the owner's response. The SuperAdmin sees all suggestions, replies and sets New, Reviewed, Planned, Done or Declined; the owner has no submission form and the server rejects owner submissions. No emails or external notifications are sent.

`/superadmin/sales` reports overall paid/free/pending/failed/refunded orders, per-currency gross sales/refunds/net earnings, each admin’s earnings, product-level sales and the latest 50 payment references for support. Amounts come from the purchase ledger in minor currency units; net is after refunds and before gateway fees or payouts. Pending and failed orders do not contribute earnings. Fully refunded sales retain their original paid-sale count. Existing transactions are backfilled, and insert/update triggers synchronize payment and refund changes. Financial snapshots survive deleting admins. The owner can toggle checkout for existing admins using the existing shared payment configuration; enabling checkout requires the configured gateway and encryption settings. This does not initiate refunds or transfer funds.

`/superadmin/settings` edits the directory brand, intro, search placeholder, section titles/descriptions, footer, accent/background, initial profile sort and featured/products/invitation-link visibility. The public homepage reads those saved settings. These are homepage presentation controls; individual profile visibility remains governed by tags and publication settings.

The editor displays the actual directory in a same-origin iframe at desktop or mobile width. Unsaved drafts update the preview immediately without database writes or view tracking. Authenticated SuperAdmin identity, message origin and parent window are checked before accepting drafts. Preview links/actions are disabled. Edits made during a slow save remain unsaved in the preview and receive an explicit message to save again.

Admin Overview has one page, with Add category, Products, Events & updates, Upload files, Orders, Enquiries and Persona conversations at the top. Profile is under Settings at `/admin/profile`. Add category opens the category form directly; each category header exposes Add offering. Switching offering editors resets the form to that offering's record.

For profile admins, returning after five minutes without input or after hiding the page refreshes a saved activity baseline. While away shows increases in paid sales, profile views, visitor question/answer pairs and contact enquiries, with currency-separated net earnings changes. It appears on Overview for roughly 9.5 seconds with a fade, supports dismissal and pause on hover/focus, and reopens through Recent activity. A first-ever visit creates the baseline without a recap. Active heartbeats run every minute. Counts are net increases, so deletions can offset additions. Email-provider messages are not integrated; contact-form enquiries are included. SuperAdmin has no personal activity recap.

The Overview assistant can read Activity analytics and display factual metrics, per-currency earnings and daily paid sales for 30 UTC calendar days (including zero-sale days), with an accessible data table. Lifetime sales include subsequently refunded purchases. Earnings are minor currency units, after refunds and before gateway fees/payouts. Insights are constructed from server records and persist with the conversation; analytics supports no write actions.

The public header shows Login to visitors and an exit icon with Dashboard and Logout options to signed-in users. Contact remains in the main profile navigation and at `/p/:slug/contact`; repeated header and home contact action buttons are removed.

Public profile, site and directory responses are not cached, so privacy updates apply to subsequent requests. Private knowledge is also checked before any chat retrieval. Existing publicly hosted image URLs remain public storage assets; the tag controls application profile and knowledge access.
